# 공공사무 운영판 0.2 — GitHub Pages + Actions

기존 `Public_Office_Jobs_v0.1_auto_refresh.zip`을 이어서 수정했습니다. ChatGPT·OpenAI API·사용자 PC 없이 GitHub에서 공식 목록 조회 → 모집단위 정리 → JSON 저장 → 화면 생성 → Pages 배포를 실행하도록 구성했습니다. 계정·저장소·공개 범위가 정해지지 않아 실제 배포와 예약 실행은 아직 활성화하지 않았습니다.

## 처음 할 일

`deployment/README_GITHUB.md`의 버튼별 안내를 따르세요. 이 **배포용 패키지의 내용만** 새 저장소 루트에 넣습니다. 이전 ZIP의 원문·첨부·실행 기록·AI 검토 규칙은 업로드하지 않습니다. 별도 제공 HTML은 현재 화면을 보는 용도이며, 운영 사이트 주소는 Pages 첫 배포 후 생성됩니다.

## 기본 동작

- 공개 페이지를 열거나 새로고침하면 같은 사이트의 `data/notices.json`을 캐시 우회 요청으로 읽습니다. 실패하면 HTML에 포함된 마지막 게시본을 보여주고 실패를 표시합니다. 브라우저가 JOB-ALIO를 직접 수집하지는 않습니다.
- Python 표준 라이브러리만 사용합니다. API 키, OpenAI 계정, 추가 Python 패키지가 필요하지 않습니다.
- JOB-ALIO 비정규직·경영회계사무 필터, 최근 60일 등록·진행중 목록이 새 공고 발견 범위입니다. 목록 1페이지와 저장된 다음 페이지를 조회합니다. 목록 이동 중 순서가 바뀔 수 있으며 전체 시장을 빠짐없이 수집한다고 보장하지 않습니다.
- 회당 목록 최대 2페이지·상세 최대 4건·원격 요청 최대 6회·신규 반영 최대 2건, 요청 간격 1초 이상, 응답당 2MB·회차 8MB, 요청당 20초 한도입니다. 재시도·리디렉션·접근 제한 우회는 없습니다.
- 미처리 후보, 다음 목록 페이지, 공고 ID, 이전 결과와 비교 해시, 마지막 시도·성공 시각을 저장합니다. AI 규칙 파일 없이 명확한 사무 모집단위를 추가합니다. 불명확한 단위는 대기 상태로 보존합니다.
- 이미 발견한 후보는 처리 전에 마감되어도 대기열에서 버리지 않습니다. 이후 상세 확인에 성공하면 지난 공고로 추가합니다. 사무 모집단위를 확정하지 못한 일부 공고는 별도의 정리 대기 영역에서 공식 링크와 미확인 사유를 표시합니다.
- 저장된 마감 공고도 확인합니다. 최근 마감 또는 결과 미확인 공고는 하루 간격의 확인 대상, 오래된 결과 확인 공고는 30일 간격의 확인 대상입니다. 처리 슬롯을 나누고 오래 기다린 공고부터 순환하므로 이 간격은 모든 공고의 완료 보장 시간이 아닙니다.
- 결과 표만 바뀐 경우 기존 컴활·영어·급여 조건과 검토시각을 보존하면서 정확히 일치하는 모집단위의 공식 경쟁률·전형별 인원을 갱신합니다. 다른 모집단위나 공고 전체 인원을 대입하지 않습니다.
- 본문 조건이 바뀌었으나 새 조건을 안전하게 해석하지 못하면 이전 조건의 현재 적용 여부를 미확인으로 표시합니다. 실패 때문에 공고 자체를 삭제하지 않습니다.

## 화면과 해석 범위

현재 공고, 모집단위 상세, 지난 공고·경쟁률 화면과 기존 디자인을 유지했습니다. 마지막 수집 성공, 이번 실행 상태, 조회 범위·대기 건수, 미확인·추출 실패를 표시합니다. 화면 생성 시각은 원문 또는 첨부 검토 시각이 아닙니다.

공식 경쟁률의 산식·범위가 확인된 동일 정의 그룹만 낮은 순 정렬 대상으로 삼습니다. 현재 저장 표본의 경쟁률 산식은 미확인이므로 정렬에 쓸 수 없습니다. 컴활·영어 배점과 필수요건은 보존하지만 통합 점수나 가중치를 만들지 않습니다. 현재 공고의 과거 비교자료는 검증된 연결이 없으면 ‘비교자료 없음’으로 남습니다.

첨부 PDF/HWP의 내용은 운영 코드가 자동 해석하지 않습니다. 기존 별도 AI 검토값은 출처·범위와 함께 보존하지만 새 공고에 AI 검토를 요구하지 않습니다. 같은 첨부 URL의 파일 내용만 교체되는 정정은 감지하지 못합니다. 마감 결과가 별도 첨부에만 공개되거나 모집단위 이름이 바뀌면 자동 연결하지 못할 수 있습니다.

## 저장·실패 처리

- 저장소의 `data/notices.json`, `refresh_state.json`, `refresh_status.json`, 필요한 경우 `refresh_error.json`을 명시적으로 커밋합니다. 임시 캐시는 유일한 저장소가 아닙니다. Git 이력에 이전 커밋이 남습니다.
- 공개 사이트에는 `dist/index.html`, `dist/data/notices.json`, `dist/.nojekyll`만 게시합니다. 원문 파일, 수집 대기 목록, 로컬 경로, 전체 로그와 이전 검토 레코드는 사이트에 싣지 않습니다.
- Actions 동시 실행을 직렬화하고 로컬 수집에는 OS 파일 잠금을 사용합니다. 데이터 푸시가 충돌하면 강제 덮어쓰기 없이 실패하고 배포하지 않습니다.
- 일부 수집 실패는 성공한 공고만 반영하고 실패한 기존 자료를 보존합니다. 전체 수집 실패는 기존 자료와 마지막 성공시각을 유지하며 실패 상태를 게시할 수 있습니다. 실패를 ‘신규 공고 없음’으로 해석하지 않습니다.
- 마지막 수집 성공시각은 해당 회차의 판독·대응까지 모두 정상인 실행을 뜻합니다. 정상 수신 후 모집단위 대응이 불명확한 부분 성공은 이번 시도시각과 개별 본문 수신시각에 남고 마지막 완전 성공시각은 유지합니다.
- 401·403·429 또는 접근 제한 본문을 받으면 해당 출처 요청을 중지하고 중지 상태를 저장합니다. 관리자 검토 없이 다음 실행에서 자동 해제하지 않습니다.
- 빌드·커밋·배포 자체가 실패하면 기존 게시본이 남아 이번 실패가 웹에 아직 표시되지 않을 수 있습니다. 이 경우 Actions 실행 상태가 기준입니다.

## 실행 명령과 파일

```text
python build.py
python collector/refresh.py
python deployment/run_ci.py --collect true
```

첫 명령은 저장 JSON으로 화면만 생성합니다. 두 번째는 실제 공식 요청을 실행합니다. 세 번째는 Actions와 같은 수집·공개 데이터 정리·빌드 작업이며 Git 푸시·배포는 별도 workflow 단계입니다. 반복해서 실행하면 회차당 요청 한도가 각각 적용됩니다.

`python build.py` 후 `index.html`을 더블클릭하면 저장본을 볼 수 있습니다. HTTP 새로고침 동작을 로컬에서 보려면 `python -m http.server 8000 --directory dist` 후 `http://localhost:8000`을 여세요. 운영 사이트는 GitHub Pages에 게시된 주소로 접속하며 PC 설치가 필요 없습니다.

주요 수정 파일: `collector/refresh.py`, `collector/auto_normalize.py`, `build.py`, `ui/`, `deployment/`, `.github/workflows/refresh-pages.yml`.

실행·재생·가상 시험과 미검증 항목은 `VERIFICATION.md`를 확인하세요. 예약은 기본 6시간 간격(UTC 00:17·06:17·12:17·18:17, 한국 09:17·15:17·21:17·03:17)으로 준비했지만 활성화 변수는 기본 꺼짐입니다. GitHub 예약은 지연될 수 있고 비활성 저장소에서는 중지될 수 있으므로 실제 실행 이력을 별도로 확인합니다. 유료 기능은 사용하지 않습니다.
